# TDD-воркфлоу

Ты остаёшься [оркестратором](../../roles/orchestrator.md). Тестировщик, кодер и ревьюер — отдельные сабагенты, которых вызываешь ты; не разыгрывай эти роли последовательно в одном контексте. Их инструкции: [тестировщик](../../roles/tester.md), [кодер](../../roles/coder.md), [ревьюер](../../roles/reviewer.md). Читай роль при назначении соответствующего исполнителя.

## 1. Контракт и исходное состояние

Зафиксируй цель, критерии приёмки, публичные точки входа, область изменений и команды проверок. Сними исходный `git status`, проверь исходное состояние затрагиваемых проверок. Существующие сбои отдели от новой задачи; не называй их RED новой функциональности.

Создай сабагентов с чистым контекстом (`fork_turns="none"` или эквивалент). Передай им контракт, путь своей роли и разрешённые файлы, без полной истории и чужой реализации/тестов. Исполнители работают последовательно; общего доступа к файловой системе недостаточно для гарантии изоляции, соблюдай ограничения ролей и проверяй их изменения.

В выбранном рабочем плане храни краткий статус: версия контракта, этап, RED/GREEN, команды и результаты, `check_fixes_used=0`, `review_fixes_used=0`, следующий шаг. Для локальной задачи, не относящейся к планам исследования, веди это в отчётах текущего чата; не создавай третий входной план.

## 2. Тестировщик → RED

1. Вызови тестировщика. Он сам определяет нужные уровни тестирования и сначала пишет тесты по контракту, не открывая реализацию.
2. Сам запусти новые/изменённые тесты. Убедись, что runner действительно выполнил нужные проверки и падение связано с отсутствующим поведением. Сбой окружения, синтаксиса теста, конфигурации runner или случайного импорта не считается RED. Отсутствующий публичный API допустим только как явно предусмотренная контрактом причина.
3. Сохрани команду и доказательство RED до любых изменений реализации. Если тесты уже зелёные, проверь, реализовано ли требование; не создавай искусственное падение и не поручай ненужный код.
4. Ошибки тестов/инфраструктуры верни ответственному исполнителю; не переходи к реализации до действительного RED. Каждое корректирующее поручение расходует общий бюджет исправлений проверок ниже.

## 3. Кодер → проверки оркестратора

Передай кодеру контракт и факт подтверждённого RED, без текста тестов, snapshots и исходников в логах. Кодер реализует поведение, тесты не читает и не запускает.

После его ответа сам последовательно выполни:

1. `pnpm typecheck`.
2. `pnpm lint`.
3. `pnpm test:unit`.
4. Все дополнительные наборы, которые выбрал тестировщик для задачи, например `pnpm test:e2e`; команды новых уровней должны быть включены и в `pnpm test:all`.

Если есть сбой, очисти диагностику от исходников тестов и передай кодеру нарушение контракта. Доказанную ошибку теста исправляет только тестировщик, без доступа к реализации; требования при этом не ослабляются. После исправления повтори весь этот набор проверок. Только GREEN позволяет перейти к ревью.

## 4. Ревьюер → исправления

Вызови ревьюера с контрактом, итоговым diff и результатами проверок. При `CHANGES_REQUESTED` передай обязательные дефекты кодеру без исходников тестов. После исправлений снова выполни этап 3, затем повторное ревью. Изменение тестов тоже требует прогонов и повторного ревью. Изменение самого контракта требует нового RED и согласования с пользователем, а не подмены ожиданий.

## 5. Лимиты и остановка

Первичная реализация и первичное ревью не расходуют попытку исправления. Есть два счётчика на весь запуск:

- `check_fixes_used`: максимум **3 дополнительных поручения исправить сбои проверок**, включая ошибки подготовки RED и финального хука.
- `review_fixes_used`: максимум **3 дополнительных поручения исправить замечания ревью**.

Увеличивай соответствующий счётчик перед поручением исправления. Счётчики не обнуляются при смене этапа, исполнителя, повторном RED или ревью. Исправление по ревью расходует бюджет ревью; отдельный сбой последующих проверок — бюджет проверок. После третьего исправления обязательно проверь результат; если он снова неуспешен, остановись. Не создавай нового агента ради обхода лимита.

При исчерпании любого бюджета прерви цепочку, сохрани изменения для разбора и сообщи: этап, причину, фактический результат, использованные попытки и что требуется дальше. Не отключай проверки и не объявляй задачу готовой. Недоступность среды сообщай отдельно от дефекта кода; не трать попытки на неизменённый повтор команды.

## 6. Финальный хук

После `APPROVED` сам выполни **`pnpm check`**: TypeScript, линтер и все тесты, включая E2E. Это тот же общий набор, который вызывает `.husky/pre-commit`. Не запускай коммит для вызова хука.

Сбой финального хука возвращает процесс к исправлению с оставшимся бюджетом; после изменений нужны проверки, повторное `APPROVED` и полный хук. Успех — только при зелёном хуке на последней версии файлов. В ответе укажи реализованное, доказательства RED → GREEN, вердикт ревьюера, итог хука и остаточные ограничения.
