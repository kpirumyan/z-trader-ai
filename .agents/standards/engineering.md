# Общие требования к инженерной работе

Читай один раз при работе по роли; применяй только относящиеся к задаче требования. Этот файл — единственный источник общих правил качества и использования документации, роли задают собственные обязанности, workflow — порядок исполнения.

## Документация и выбор технологий

Перед проектированием, реализацией, написанием тестов или ревью определи затронутые технологии и установленные версии по манифесту и lockfile. Изучи относящиеся к решению разделы официальной документации каждой из них: React, Next.js, TypeScript, библиотек UI, состояния, хранения, запросов и тестирования — в пределах задачи, а не только Next.js. Для Next.js используй также поставляемые руководства в `node_modules/next/dist/docs/`. Сопоставляй документацию с установленной версией; учитывай ограничения, устаревшие и экспериментальные API. Если источник недоступен или совместимость не подтверждена, явно обозначь пробел и его влияние, не выдавай предположение за проверенный факт.

В результате своей стадии укажи кратко: технология/версия, ссылка или локальный путь и раздел, какое решение основано на источнике. Не копируй руководства. Каждый исполнитель проверяет относящиеся к своей работе основания, ссылки предыдущего агента не заменяют оценку. Для тестов это включает используемые возможности runner, библиотеки компонентов, ожидания, изоляцию и моки.

## Архитектура и реализация

- Определяй ответственности и поток данных до изменения кода. Разделяй UI, работу с данными, хранение состояния и взаимодействия по осмысленным границам. Не складывай независимые обязанности в один компонент; не дроби код на бессодержательные обёртки ради количества файлов.
- В Next.js сохраняй серверное выполнение там, где оно подходит; клиентские границы ограничивай необходимой интерактивностью и браузерными API. Обосновывай размещение состояния, получение данных и изменения данных, учитывай гидратацию и доступность данных на сервере.
- Рассматривай подходящие возможности установленного React и Next.js, включая Server Components, Server Actions, Suspense и актуальные хуки. Выбор должен решать конкретную задачу и соответствовать документированным условиям API. Не заменяй архитектуру обязательным применением новых функций; не используй устаревший шаблон по привычке, если поддерживаемый подход лучше отвечает требованиям.
- Используй эффекты для необходимой синхронизации с внешними системами; избегай дублирования состояния и скрытых зависимостей. Сложность, зависимости и масштаб рефакторинга должны быть оправданы текущей задачей.

## Пользовательское поведение и приёмка

Для затронутого сценария определи начальное отображение, загрузку, готовность, пустой результат, ошибку и восстановление. Учитывай обновление страницы и сохранённые предпочтения, если они участвуют в сценарии. Оценивай визуальную стабильность, доступность, фокус и сохранение управления.

Устранение симптома не является приёмкой, если решение создаёт другой дефект: пропадание нужных элементов, неверное промежуточное состояние, потерю ввода или пустую область без понятного состояния загрузки. Заглушка, временная недоступность или скрытие требуют основания в пользовательском сценарии; проверяй итоговое поведение целиком. Не закрепляй конкретный обходной приём в контракте без такого основания.

Любая роль обязана оспорить дефект в требованиях, архитектуре или доказательствах и описать пользовательское последствие. Соответствие контракту и зелёные тесты сами по себе не доказывают качество решения. Обязательное замечание должно указывать конкретный риск/нарушение и способ проверки, а не личное предпочтение.
