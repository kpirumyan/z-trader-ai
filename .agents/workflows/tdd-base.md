# Общая основа TDD

Этот файл исполняется через один из двух входных скиллов; самостоятельной команды у него нет. Входной скилл задаёт `architecture=required` или `architecture=none`. Порядок этапов, передача контекста, проверки и лимиты определены только здесь.

## 1. Контракт и исходное состояние

Зафиксируй пользовательскую цель, наблюдаемое поведение, критерии приёмки, публичные точки входа, область изменений и команды проверок. Сохрани исходную формулировку пользовательской задачи для независимой оценки исполнителями. Отдели требования пользователя от предложенного способа реализации. Для UI включи начальное отображение, загрузку, готовность, ошибки и повторный вход, если они затронуты задачей. Укажи, какие элементы должны оставаться видимыми и доступными; устранение одного симптома не должно подменять весь результат. Сними исходный `git status`, проверь исходное состояние затрагиваемых проверок. Существующие сбои отдели от новой задачи; не называй их RED новой функциональности.

Назначаемые роли и профили Codex: [архитектор](../roles/architect.md) — `agent_type="architect"` (`.codex/agents/architect.toml`), [тестировщик](../roles/tester.md) — `agent_type="tester"` (`.codex/agents/tester.toml`), [кодер](../roles/coder.md) — `agent_type="coder"` (`.codex/agents/coder.toml`), [ревьюер](../roles/reviewer.md) — `agent_type="reviewer"` (`.codex/agents/reviewer.toml`). Читай роль при назначении исполнителя. Это отдельные сабагенты; не разыгрывай их в одном контексте.

Создай сабагентов через указанные профили (`agent_type`) с чистым контекстом (`fork_turns="none"` или эквивалент). Не передавай `model` и `reasoning_effort` при запуске: их значения задают файлы профилей. Убедись, что инструмент распознал выбранный профиль; если он недоступен, не заменяй его встроенным агентом, а сообщи об ограничении. Передай исполнителям исходную пользовательскую задачу, контракт, путь назначенной роли, разрешённые файлы и ссылки на относящиеся к задаче источники с версиями. Тестировщик и кодер получают одну версию контракта независимо. Архитектурный документ передавай без исходников реализации и тестов; ограничения доступа заданы ролями. Не передавай полную историю. Оркестратор может читать обе стороны для проверки и очистки диагностики. Исполнители работают последовательно; общего доступа к файловой системе недостаточно для гарантии изоляции, соблюдай ограничения ролей и проверяй их изменения.

В выбранном рабочем плане храни краткий статус: выбранный вход, версия контракта, архитектурное решение (если есть), этап, RED/GREEN, команды и результаты, `check_fixes_used=0`, `review_fixes_used=0`, следующий шаг. Для локальной задачи, не относящейся к планам исследования, веди это в отчётах текущего чата; не создавай третий входной план.

## Архитектурный этап

При `architecture=required` до назначения тестировщика вызови архитектора по его роли. Передай пользовательскую задачу, черновой контракт, ограничения и пути реализации. Он исследует текущую структуру и документацию, возвращает решение с обоснованием и критериями приёмки. До вердикта `READY` к тестам и реализации не переходи. При `NEEDS_INPUT` получи недостающие сведения; вопрос пользователю нужен только для существенного продуктового выбора, который нельзя вывести из его указаний.

При `architecture=none` отдельного архитектора не вызывай. Этот маршрут подходит для локального изменения с определёнными границами и уже обоснованным решением. Если обнаружен нерешённый архитектурный выбор — например, распределение состояния, серверной и клиентской ответственности или поведения загрузки — останови эту цепочку как незавершённую, сообщи причину и предложи отдельный запуск `$tdd-architecture`. Не переключай явно выбранную команду молча и не требуй архитектора только из-за названия API.

Архитектурное решение является проверяемым предложением. Оркестратор сверяет его с пользовательской целью; любой исполнитель вправе указать дефект в нём. Принятое решение и критерии получают версию; код тестов и реализации в документ решения не включай.

## 2. Тестировщик → RED

1. Вызови тестировщика. Он сначала оценивает полноту контракта по пользовательской цели, затем определяет нужные уровни и пишет тесты по контракту, не открывая реализацию.
2. Сам запусти новые/изменённые тесты. Убедись, что runner действительно выполнил нужные проверки и падение связано с отсутствующим поведением. Сбой окружения, синтаксиса теста, конфигурации runner или случайного импорта не считается RED. Отсутствующий публичный API допустим только как явно предусмотренная контрактом причина.
3. Сохрани команду и доказательство RED до любых изменений реализации. Если тесты уже зелёные, проверь, реализовано ли требование; не создавай искусственное падение и не поручай ненужный код.
4. Ошибки тестов/инфраструктуры верни ответственному исполнителю; не переходи к реализации до действительного RED. Каждое корректирующее поручение расходует общий бюджет исправлений проверок ниже.

## 3. Кодер → проверки оркестратора

Передай кодеру контракт и факт подтверждённого RED, без текста тестов, snapshots и исходников в логах. Кодер реализует поведение, тесты не читает и не запускает.

После его ответа сам последовательно выполни:

1. `pnpm typecheck`.
2. `pnpm lint`.
3. `pnpm test:unit`.
4. Все дополнительные наборы, которые выбрал тестировщик для задачи, например `pnpm test:e2e`; команды новых уровней должны быть включены и в `pnpm test:all`.

Если есть сбой, очисти диагностику от исходников тестов и передай кодеру нарушение контракта. Доказанную ошибку теста исправляет только тестировщик, без доступа к реализации; требования при этом не ослабляются. После исправления повтори весь этот набор проверок. Только GREEN позволяет перейти к ревью.

## 4. Ревьюер → исправления

Вызови ревьюера с исходной пользовательской задачей, контрактом, архитектурным решением (если есть), итоговым diff, источниками и результатами проверок. Он независимо оценивает и решение, и реализацию. При `CHANGES_REQUESTED` направь дефект ответственному: кодеру — реализацию без исходников тестов, тестировщику — ошибку теста, архитектору — архитектуру при `architecture=required`. Для архитектурного дефекта в маршруте без архитектора действуют правила выбора маршрута выше. После пересмотра архитектуры получи `READY`, обнови контракт и повтори затронутые этапы. После исправлений снова выполни этап 3, затем повторное ревью. Изменение тестов тоже требует прогонов и повторного ревью. При изменении контракта сохрани исходные требования пользователя и передай новую версию обоим исполнителям. Новые или изменённые требования к поведению проходят RED до кода; уже доказанный RED не создавай заново искусственно. Согласуй с пользователем изменение продуктового поведения или границ задачи, если оно не было разрешено; техническое уточнение внутри согласованных требований выполняй самостоятельно. Не ослабляй критерии ради GREEN.

## 5. Лимиты и остановка

Первичная реализация и первичное ревью не расходуют попытку исправления. Есть два счётчика на весь запуск:

- `check_fixes_used`: максимум **3 дополнительных поручения исправить сбои проверок**, включая ошибки подготовки RED и финального хука.
- `review_fixes_used`: максимум **3 дополнительных поручения исправить замечания ревью или архитектурного разбора**. Сюда входит возврат архитектору для пересмотра решения; передача уже исправленного решения на следующую штатную стадию не является отдельной попыткой.

Увеличивай соответствующий счётчик перед поручением исправления. Счётчики не обнуляются при смене этапа, исполнителя, повторном RED или ревью. Исправление по ревью расходует бюджет ревью; отдельный сбой последующих проверок — бюджет проверок. После третьего исправления обязательно проверь результат; если он снова неуспешен, остановись. Не создавай нового агента ради обхода лимита.

При исчерпании любого бюджета прерви цепочку, сохрани изменения для разбора и сообщи: этап, причину, фактический результат, использованные попытки и что требуется дальше. Не отключай проверки и не объявляй задачу готовой. Недоступность среды сообщай отдельно от дефекта кода; не трать попытки на неизменённый повтор команды.

## 6. Финальный хук

После `APPROVED` сам выполни **`pnpm check`**: TypeScript, линтер и все тесты, включая E2E. Это тот же общий набор, который вызывает `.husky/pre-commit`. Не запускай коммит для вызова хука.

Сбой финального хука возвращает процесс к исправлению с оставшимся бюджетом; после изменений нужны проверки, повторное `APPROVED` и полный хук. Успех — только при зелёном хуке на последней версии файлов. В ответе укажи реализованное, доказательства RED → GREEN, вердикт ревьюера, итог хука и остаточные ограничения.
