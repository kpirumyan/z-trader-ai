# Z-TraderBot

- Пиши по-русски. Используй Git Bash и pnpm.
- Терминал в первой версии только англоязычный: весь видимый интерфейс терминала, включая меню, подписи, сообщения и состояния, пиши на английском.
- Никогда не создавай временные файлы, скрипты и другие вспомогательные артефакты в рабочей директории проекта; используй выделенную scratch/temp-папку текущей задачи.
- Главный агент по умолчанию — [оркестратор](.agents/roles/orchestrator.md); для обсуждения и планирования архитектуры главным агентом также может быть выбран [архитектор](.agents/roles/architect.md) (`architect`). Сабагент читает назначенную ему роль; не становится оркестратором.
- Если workflow или пользовательское поручение требует сабагента, запускай его по `name` подходящего профиля: в Antigravity — через `invoke_subagent` (`TypeName="<name>"` из `.agents/agents/*.md`), в Codex — с `agent_type="<name>"` из `.codex/agents/*.toml`. Не используй для проектных ролей встроенные `self`/`research`/`default`/`worker`/`explorer` или только текстовое назначение роли. Если нужного профиля нет, сначала добавь его конфиг; модель, инструменты и инструкции бери из профиля без ручных переопределений при запуске. Передавай задачу с чистым контекстом (`fork_turns="none"` в Codex; в Antigravity `invoke_subagent` создаёт чистый контекст по умолчанию).
- [Архитектор](.agents/roles/architect.md) (`architect`) может запускаться как главный агент для обсуждения и планирования или вызываться оркестратором как сабагент в `$tdd-architecture`. [Исследователь](.agents/skills/researcher/SKILL.md) — только для исследования большой задачи или её подзадач. Не загружай исследовательский скилл для обычной реализации, проверки или организации файлов.
- Для большой задачи используй [глобальный план](.agents/plans/global.md); для обнаружения диапазонов/каналов — [план диапазонов](.agents/plans/range-detection.md). Читай только план выбранной задачи. При общем «продолжай проект» начни с глобального плана.
- Для локальной правки, проверки ссылки или организации файлов читай только затронутые документы; планы нужны лишь при изменении их содержания.
- Ссылки — указатели, не команда загрузить всё. Дополнительные файлы читай только при условии, указанном рядом со ссылкой; не обходи ссылки рекурсивно и не перечитывай неизменённый контекст.
- Текущий статус и следующий шаг хранятся в выбранном плане. Согласованные решения и проверенные результаты фиксируй в предназначенных для них документах по правилам плана; гипотезы не отмечай как результаты.
- [Реестр задач](.agents/plans/tasks.md) — единый источник истины (SSOT) для состава, кодов, статусов ([x]/[ ]) и текущего шага всех задач. Планы и архитектурные контракты описывают цели, архитектуру, спецификации и критерии приёмки, ссылаясь на реестр задач, и не дублируют чеклисты или логи прогонов.
- При завершении задачи или этапа обязательно проведи ревизию затронутых файлов задач, планов и архитектурных контрактов: обнови статусы и текущий шаг в реестре задач (свернув промежуточные подзадачи завершённого этапа), оставь в планах только актуальные решения и статус, а из архитектурных контрактов удали временные планы проектирования конкретной задачи (пофайловые перечни, сигнатуры и промежуточные шаги), сохранив только действующие архитектурные инварианты и критерии приёмки.
- Стандарт структуры кодовой базы (Layout Standard):
  - `app/types/` — строго для типов и интерфейсов TypeScript (`type`, `interface`). Никакого рантайм-кода, констант и функций. Все доменные типы объявляются здесь, а не внутри файлов фичей.
  - `app/constants/` — неизменяемые константы, маппинги и статические справочники.
  - `app/hooks/` — пользовательские React-хуки (`use*`).
  - `app/components/` — React-компоненты представления.
  - `app/<feature>/` — реализация бизнес-логики и провайдеры (импортируют типы из `app/types/`).
  - `tests/unit/` и `tests/e2e/` — модульные и сквозные тесты. Продакшен-код не импортирует ничего из `tests/`.
  - Запрещено смешивать типы с кодом: не объявляй публичные доменные типы в файлах реализаций и не импортируй типы из файлов с кодом/данными.
- Стандарт именования файлов (Naming Conventions):
  - Файлы типов, компонентов и констант доменных сущностей именуются строго в **единственном числе** (`singular`, `kebab-case`): `terminal-window.ts`, `terminal-window.tsx`, `instrument.ts`, `workspace.ts`, `storage.ts`, `theme.ts`.
  - Правило соответствия 1-в-1: имя файла в `app/types/<entity>.ts` совпадает с `app/constants/<entity>.ts` и `app/components/<entity>.tsx` (запрещено смешивать `terminal-windows` в одном месте и `terminal-window` в другом).
  - Множественное число (`plural`) допустимо только для категориальных папок (`types/`, `constants/`, `components/`, `hooks/`, `tests/`) и для хуков/функций, оперирующих коллекцией (`use-workspace-windows.ts`).
  - Общие константы (ключи хранилищ, лимиты, задержки) импортируются и используются **напрямую** из `@/app/constants/*`, без создания лишних локальных псевдонимов (`const FOO = FOO_BAR;`).
- Стандарт читаемости и форматирования кода (Code Style & Formatting Standard):
  - Код форматируется через Prettier и ESLint (`pnpm format`, `pnpm lint:fix`); не оставляй сплошной текст без отступов и многострочные перегруженные JSX-конструкции на одной строке.
  - Вертикальный ритм в логике: обязательное логическое разделение пустой строкой между разнородными блоками (группы хуков, локальные переменные, вычисления); обязательная пустая строка перед блоком `return` и вокруг составных блоков (`if`, циклы, `useEffect`).
  - Форматирование и декомпозиция JSX: отделяй пустой строкой крупные структурные секции (`header`, `content`, `footer`) и блоки условного рендеринга (`{condition && (...) }`); компактные списки тегов и кнопок держи слитно; если дочерний блок разрастается более чем на ~25–30 строк, выноси его в отдельный компонент в `app/components/`.
- Проверки: `pnpm format:check`, `pnpm typecheck`, `pnpm lint`, `pnpm test:unit`, `pnpm test:e2e`. Полный хук: `pnpm check` (Prettier → TypeScript → ESLint → все тесты); также запускается Husky перед коммитом.
